# 帰納的推論プロンプト

複数の具体的な観察や事例から共通のパターンを抽出し、一般的な法則や原則を導き出してください。個別の事象から全体を理解するアプローチで、バグパターンの発見、共通処理の抽出、ベストプラクティスの形成を行います。

## 実行手順

### 1. 事例の収集

推論の基礎となる具体的な事例やデータを系統的に集めます：

**観察対象の明確化**:

- 何について一般化したいのか（バグパターン、コード構造、ユーザー行動など）
- 観察の目的と仮説
- 調査範囲の設定（時間範囲、コード範囲、データ量）

**多様な事例の収集**:

- 少なくとも3-5件以上の事例を集める
- 異なる状況下での事例を含める
- 成功事例と失敗事例の両方
- 極端なケースや例外的なケースも含める
- バイアスを避けるため、意図的に多様性を確保

**バグパターン収集の例**:

```
事例1: ユーザー入力フォームでのXSS脆弱性
事例2: API入力でのSQLインジェクション
事例3: ファイルアップロードでのパストラバーサル
事例4: コメント欄でのHTMLインジェクション
事例5: 検索機能でのコマンドインジェクション
```

**コード重複の事例**:

```typescript
// 事例1: ユーザー作成
async function createUser(data) {
  const valid = validateUserData(data);
  if (!valid) throw new Error('Invalid data');
  const result = await db.users.insert(data);
  await audit.log('user_created', result.id);
  return result;
}

// 事例2: プロジェクト作成
async function createProject(data) {
  const valid = validateProjectData(data);
  if (!valid) throw new Error('Invalid data');
  const result = await db.projects.insert(data);
  await audit.log('project_created', result.id);
  return result;
}

// 事例3: タスク作成
async function createTask(data) {
  const valid = validateTaskData(data);
  if (!valid) throw new Error('Invalid data');
  const result = await db.tasks.insert(data);
  await audit.log('task_created', result.id);
  return result;
}
```

### 2. 共通パターンの探索

集めた事例から共通する要素や構造を抽出します：

**類似性の特定**:

- 複数の事例に共通して現れる要素は何か
- 同じ構造やフローが繰り返されていないか
- 似たような変数名、関数名、パターンはないか
- 共通のエラーメッセージや兆候はないか

**差異の分析**:

- 事例間で異なる部分は何か（これは可変部分）
- 変化する部分と変化しない部分の区別
- パラメータ化できる部分の特定
- コンテキストによる違いの理解

**抽象化のレベル**:

- どのレベルで共通性を見出すか
- 表面的な類似性（構文レベル）
- 構造的な類似性（アーキテクチャレベル）
- 意味的な類似性（目的やドメインレベル）

**バグパターンの抽象化例**:

```
共通パターン: 「外部からの入力が適切に検証・サニタイズされずに使用されている」

具体的な表れ:
- XSS: HTML/JavaScript として解釈される
- SQLi: SQL として解釈される
- パストラバーサル: ファイルパスとして解釈される
- コマンドインジェクション: シェルコマンドとして解釈される

一般原則: 「信頼できない入力は、インタプリタに渡す前に検証・エスケープが必須」
```

**コード重複の抽象化例**:

```
共通パターン:
1. データのバリデーション
2. エラー時の例外スロー
3. データベースへの挿入
4. 監査ログの記録
5. 結果の返却

可変部分:
- バリデーション関数（エンティティごとに異なる）
- データベーステーブル（エンティティごとに異なる）
- ログのイベント名（エンティティごとに異なる）

不変部分:
- 全体の処理フロー
- エラーハンドリングの方法
- 非同期処理の構造
```

### 3. 一般原則の仮説

観察から導かれる一般的な法則や原則を仮説として定式化します：

**仮説の定式化**:

- 「すべての〇〇は△△である」という形式
- 具体例から独立した抽象的な表現
- 明確で検証可能な形
- 適用範囲の明示

**原則の階層化**:

- より一般的な上位原則
- 特定のコンテキストでの下位原則
- 例外や条件の明確化

**バグパターンからの仮説**:

```
仮説: 「すべての外部入力は、使用前に検証とエスケープが必要」

詳細化:
- レベル1: データの出所に基づく分類（外部 vs 内部）
- レベル2: 使用方法に基づく処理（表示、クエリ、実行など）
- レベル3: 各使用方法に応じた適切な対策

適用範囲: Webアプリケーションのすべてのユーザー入力
例外: システム内部で生成された信頼できるデータ
```

**コード重複からの仮説**:

```
仮説: 「エンティティのCRUD操作は共通のパターンに従う」

一般化された処理フロー:
1. 入力の検証
2. ビジネスロジックの適用
3. データストアの操作
4. 副作用の処理（ログ、通知など）
5. 結果の返却

リファクタリング方針:
- 共通フローをテンプレートメソッドパターンで抽出
- 可変部分は戦略パターンで差し替え可能にする
- 各エンティティは特定の戦略を注入
```

### 4. 反例の確認

仮説が本当に一般的に成り立つか、反例を探して検証します：

**反例の探索**:

- 仮説に当てはまらないケースはないか
- 意図的に反例を探す（falsification）
- エッジケースや特殊な状況での検証
- 異なるコンテキストでの適用可能性

**仮説の精緻化**:

- 反例が見つかった場合、仮説を修正
- 適用条件を追加（「〇〇の場合に限り」）
- 例外を明示（「△△を除き」）
- より正確で限定的な原則へ

**バグパターンの検証**:

```
仮説: 「すべての外部入力は検証が必要」

反例の探索:
Q: 信頼されたAPI（例: 社内の別システム）からの入力も？
A: Yes、原則として検証すべき（防御的プログラミング）
   ただし、検証レベルは調整可能

Q: 設定ファイルからの読み込みは？
A: 設定ファイルも外部入力と見なすべき
   管理者が編集するため、typoやエラーの可能性

Q: 環境変数は？
A: 環境変数も検証対象
   デプロイ時の設定ミスを検出

精緻化された仮説:
「システム境界を越えるすべての入力は、信頼性に関わらず検証すべき。
 検証の厳格さは、データの出所と使用方法によって調整する。」
```

**コードパターンの検証**:

```
仮説: 「すべてのCRUD操作は同じパターン」

反例の探索:
Q: バッチ処理（複数レコードの一括操作）は？
A: 基本パターンは同じだが、バリデーションとロギングの粒度が異なる
   → パターンを拡張して対応

Q: 更新時の楽観的ロックは？
A: 基本パターンに「バージョンチェック」ステップを追加
   → パターンはフックポイントで拡張可能にする

Q: ソフトデリートと物理削除の違いは？
A: 「データストアの操作」ステップの実装が異なる
   → 戦略パターンで切り替え

精緻化された設計:
- 基本パターン + 拡張ポイント（hooks）
- 標準的なステップは共通化
- 特殊な処理はオプショナルなフックで追加
```

- 再利用可能な抽象化
- 予測や意思決定に使える原則
- 新しい状況への適用可能な知識

### 再利用可能な知見

- ベストプラクティス

## 注意事項

### サンプルサイズの重要性

- 少数の事例からの一般化は危険
- 統計的に有意なサンプル数を確保
- 少なくとも3-5件、できれば10件以上
- 多様性を持ったサンプル選択

### 早まった一般化の危険

- 偶然の一致を必然と誤認しない
- 「すべて」「常に」という表現は慎重に
- 反例を積極的に探す
- 適用範囲を明確にする

### 相関と因果の混同

- AとBが同時に起こる ≠ AがBの原因
- 第三の要因が両方に影響している可能性
- 因果関係の証明には追加の分析が必要
- 実験や介入で因果を確認

### 確証バイアス

- 自分の仮説を支持する事例ばかり集めがち
- 意図的に反例を探す姿勢
- 他者のレビューを受ける
- データ主導の客観的な分析
