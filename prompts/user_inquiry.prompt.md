# ユーザー質問・調査依頼プロンプト

適切な質問技法を用いてユーザーから必要な情報を効果的に引き出してください。また、タスク実行中に技術的な調査が必要になった場合は、明確かつ構造化された形でユーザーに調査依頼を行います。

## 第1部: ユーザーへの質問技法

## 使用場面

- 新規プロジェクトの要件ヒアリング
- ユーザーからのバグ報告の詳細化
- 機能改善のためのユーザーフィードバック収集
- カスタマーサポートでの問題解決
- UXリサーチやユーザーインタビュー
- 仕様変更や追加機能の検討
- トラブルシューティング時の状況確認

## 実行手順

### 0. 質問の必要性（いつ質問するか）

以下に該当する場合は、先にユーザーへ質問して不確実性を下げます（推測で埋めない）:

- 受入条件や成功条件が不明で、完成判定ができない
- スコープが曖昧で、誤った範囲を実装/調査しそう
- 重要な前提（環境・権限・データ・制約）が不明
- リスクが高い（破壊的変更/セキュリティ/運用影響）
- 代替案が複数あり、意思決定の軸が分からない

逆に、以下は質問せず進めてよい:

- 影響が小さく、後で修正可能で、デフォルトが妥当
- 既存ドキュメント/コードから根拠が取れる（質問より速い）

**質問テンプレ（構造化）**:

```markdown
## 質問
{質問本文}

## 理由
{なぜ必要か / ここが決まらないと何がブレるか}

## 選択肢
- A: {案}（メリット/デメリット）
- B: {案}（メリット/デメリット）

## デフォルト
未回答なら {A/B} で進めます（理由: {短く}）
```

### 1. 5W1Hで状況把握

まず基本的な状況を把握するため、以下の観点で情報を収集します：

- **Who（誰が）**: 影響を受けるユーザー、担当者、ステークホルダーは誰か
- **What（何を）**: 何が起きているのか、何を求めているのか
- **When（いつ）**: いつから、いつまでに、どのタイミングで
- **Where（どこで）**: どの環境、どの画面、どのシステムで
- **Why（なぜ）**: なぜそれが必要なのか、なぜ問題なのか
- **How（どのように）**: どのような方法で、どの程度の頻度で

### 2. オープン質問で広げる

ユーザーの自由な発言を促し、想定外の情報や背景を引き出します：

- 「〜について、もう少し詳しく教えていただけますか？」
- 「その時、どのような状況でしたか？」
- 「理想的には、どのような結果を期待されていますか？」
- 「他に関連することで気になる点はありますか？」

### 3. クローズド質問で絞る

具体的な確認や選択肢の絞り込みを行います：

- 「この問題は毎回発生しますか？」
- 「エラーメッセージは表示されましたか？」
- 「他のユーザーでも同じ現象が起きていますか？」
- 「A案とB案、どちらが望ましいですか？」

### 4. 確認質問で検証

理解した内容が正しいか、解釈にズレがないかを確認します：

- 「つまり、〜ということでしょうか？」
- 「私の理解では〜ですが、合っていますか？」
- 「要約すると、〜という理解で正しいでしょうか？」
- 「他に補足すべき点はありますか？」

## 期待される成果

- **正確な情報収集**: ユーザーのニーズや問題の本質を正確に把握
- **誤解の回避**: 解釈のズレを早期に発見し、手戻りを防ぐ
- **信頼関係の構築**: 適切な質問により、ユーザーとの信頼関係が強化される
- **効率的なコミュニケーション**: 必要な情報を最短時間で収集
- **潜在的ニーズの発見**: 表面的な要求の裏にある真のニーズを明らかに

## 注意事項

- **質問の順序**: いきなり細かい質問をせず、大きな視点から徐々に絞り込む
- **誘導質問の回避**: 自分の仮説を押し付けるような質問は避ける
- **傾聴の重要性**: 質問だけでなく、相手の話をしっかり聞くことが最も重要
- **専門用語の調整**: ユーザーの技術レベルに合わせた言葉選び
- **質問のタイミング**: 相手の話を遮らず、適切なタイミングで質問する
- **質問の量**: 質問攻めにならないよう、バランスを考える
- **記録の習慣**: 重要な情報は必ず記録に残す

## 例

### 例1: バグ報告の詳細化

**初期報告**: 「ログインできません」

**質問フロー**:

**5W1H（状況把握）**:

- Q: いつから、この問題が発生していますか？（When）
- A: 今朝から
- Q: どのデバイス・ブラウザを使用していますか？（Where/How）
- A: Windows PC、Chromeブラウザ
- Q: あなただけですか、他のユーザーも同じ状況ですか？（Who）
- A: 自分だけだと思います

**オープン質問（広げる）**:

- Q: ログインを試みた時、どのような画面や反応がありましたか？
- A: パスワードを入力して送信ボタンを押すと、画面が一瞬白くなって、またログイン画面に戻ります
- Q: その前後で、何か変わったことはありましたか？
- A: 昨日、パスワードを変更しました

**クローズド質問（絞る）**:

- Q: エラーメッセージは表示されますか？
- A: いいえ、何も表示されません
- Q: 新しいパスワードに変更したことは確実ですか？
- A: はい、パスワード変更の確認メールも受け取りました
- Q: パスワードマネージャーは使用していますか？
- A: はい、使っています

**確認質問（検証）**:

- Q: つまり、昨日パスワードを変更してから、新しいパスワードでログインを試みているが、エラーメッセージなしでログイン画面に戻される、ということですね？
- A: はい、その通りです

**追加確認**:

- Q: 念のため、パスワードマネージャーに保存されている値が古い可能性がありますが、手入力で新しいパスワードを試していただけますか？
- A: あ、手入力したらログインできました！パスワードマネージャーが古いパスワードを保存していたようです

**結果**: 問題の原因を特定（パスワードマネージャーの古い値）し、解決

### 例2: 新機能の要件ヒアリング

**初期依頼**: 「レポート出力機能を追加してほしい」

**質問フロー**:

**5W1H**:

- Q: レポートは誰が使用しますか？（Who）
- A: 営業マネージャーと経営層です
- Q: どのような内容のレポートですか？（What）
- A: 月次の売上データと顧客分析です
- Q: いつ使用されますか？（When）
- A: 毎月の営業会議（月初3日以内）で使用します

**オープン質問**:

- Q: 現在、レポートはどのように作成されていますか？
- A: Excelで手作業で集計しています。毎回2〜3時間かかって大変です
- Q: 理想的には、どのようなレポートが欲しいですか？
- A: ボタン一つでPDF出力できて、そのまま会議で配布できるものが理想です

**クローズド質問**:

- Q: レポートのレイアウトやデザインは決まっていますか？
- A: はい、現在のExcelフォーマットを踏襲したいです
- Q: グラフや図表は必要ですか？
- A: はい、売上推移のグラフは必須です
- Q: 過去データとの比較は必要ですか？
- A: はい、前月比と前年同月比を表示したいです

**確認質問**:

- Q: まとめると、月次売上と顧客分析を既存Excelと同じレイアウトでPDF出力し、前月比・前年同月比を含むグラフも含める、という理解で正しいですか？
- A: はい、完璧です

**結果**: 具体的で実装可能な要件定義が完成

### 例3: ユーザーフィードバックの深掘り

**初期フィードバック**: 「この画面、使いにくいです」

**質問フロー**:

**オープン質問**:

- Q: 具体的に、どの部分が使いにくいと感じますか？
- A: 欲しい情報がどこにあるか分かりにくいです
- Q: 主にどのような情報を探していますか？
- A: 直近の注文状況と在庫数です

**クローズド質問**:

- Q: 画面上部のメニューから探していますか？
- A: いいえ、ページ内をスクロールして探しています
- Q: 他の画面と比べて、この画面だけ使いにくいですか？
- A: はい、他の画面は問題ないです

**確認質問**:

- Q: つまり、注文状況と在庫数という情報が現在の画面レイアウトでは見つけにくい、ということですね？
- A: はい、できれば画面上部に固定表示してほしいです

**結果**: UI改善の具体的な方向性が明確に

## 第2部: 調査依頼の構造化

タスク実行中に技術的な不明点や外部情報の確認が必要になった場合、ユーザーに対して明確で構造化された調査依頼を行います。

### 1. 調査が必要なケース

#### 技術的な不明点

- ライブラリやフレームワークの最新API仕様が不明
- ベストプラクティスが不明
- 技術選定で複数の選択肢があり、比較情報が必要

#### 外部情報の確認

- 公式ドキュメントの確認が必要
- セキュリティ脆弱性情報の確認
- 互換性情報の確認

#### データや仕様の不明点

- データ構造やスキーマの詳細が不明
- ビジネスロジックの仕様が不明
- 既存システムの動作が不明

#### 環境や設定の不明点

- デプロイ環境の設定方法が不明
- インフラ構成の詳細が不明
- 依存関係の解決方法が不明

### 2. 調査依頼のフォーマット

ユーザーに調査を依頼する場合、以下の構造化されたフォーマットを使用してください：

#### 基本フォーマット

```markdown
## 調査が必要です

### 理由
{調査が必要な理由を1-2行で簡潔に}

### 調査内容
**トピック**: {調査すべきトピック}

**背景**:
{現在の状況や背景を説明}
- どのような作業をしているか
- なぜこの調査が必要か
- 関連する技術スタックや制約

**質問**:
1. {具体的な質問1}
2. {具体的な質問2}
3. {具体的な質問3}

### 現在の進捗
**完了**:
- {完了した項目1}
- {完了した項目2}

**次のステップ（調査後）**:
- {調査結果を待って実施する項目1}
- {調査結果を待って実施する項目2}
```

### 3. 調査依頼の例

#### 例1: ライブラリのAPI仕様確認

```markdown
## 調査が必要です

### 理由
pandas 2.0の新しいAPIドキュメントを確認する必要があります

### 調査内容
**トピック**: pandas 2.0の主要なAPI変更点とベストプラクティス

**背景**:
データ処理パイプラインをpandas 1.5から2.0に移行中です。
既存のコードで非推奨警告が出ており、最新のAPIに更新する必要があります。
特に、DataFrame.append()が削除されたため、代替方法を確認する必要があります。

**質問**:
1. pandas 2.0でDataFrame.append()の代替として推奨される方法は何か
2. pandas 2.0で非推奨になった主要なAPIは何か
3. 大量データを扱う際のメモリ効率的な処理方法は何か
4. pandas 2.0の破壊的変更で注意すべき点は何か

### 現在の進捗
**完了**:
- pandas 2.0のインストールと環境構築
- 既存コードの実行と非推奨警告の収集
- 基本的なDataFrame操作の動作確認

**次のステップ（調査後）**:
- DataFrame結合処理を最新APIに更新
- パフォーマンステストの実施
- 全体的なコードレビュー
```

#### 例2: セキュリティ脆弱性の確認

```markdown
## 調査が必要です

### 理由
使用中のライブラリに既知の脆弱性がないか確認が必要です

### 調査内容
**トピック**: requests 2.28.0のセキュリティ脆弱性とアップデート推奨

**背景**:
Webスクレイピング機能を実装中で、requestsライブラリを使用しています。
本番環境での使用を予定しているため、セキュリティ面を確認する必要があります。

**質問**:
1. requests 2.28.0に既知のセキュリティ脆弱性はあるか
2. 最新の安定版バージョンは何か
3. SSL/TLS証明書検証のベストプラクティスは何か
4. タイムアウト設定の推奨値は何か

### 現在の進捗
**完了**:
- 基本的なHTTPリクエスト機能の実装
- エラーハンドリングの実装

**次のステップ（調査後）**:
- セキュリティ設定の最適化
- リトライロジックの実装
- 本番環境向けの設定調整
```

#### 例3: AWS Lambda設定の確認

```markdown
## 調査が必要です

### 理由
AWS Lambda関数のメモリとタイムアウト設定の推奨値を確認したいです

### 調査内容
**トピック**: AWS Lambda関数のリソース設定とコスト最適化

**背景**:
画像処理を行うLambda関数を実装中です。
処理時間とメモリ使用量のトレードオフを考慮した最適な設定値を知る必要があります。

**質問**:
1. 画像処理Lambda関数の推奨メモリサイズは何か
2. タイムアウト設定の適切な値は何か
3. コスト効率を考慮したメモリとタイムアウトのバランスは何か
4. Lambda関数の同時実行数制限の設定方法は何か

### 現在の進捗
**完了**:
- 基本的な画像処理ロジックの実装
- ローカル環境でのテスト
- Lambda関数の基本的なパッケージング

**次のステップ（調査後）**:
- terraform設定ファイルの作成
- Lambda関数のデプロイ
- 本番環境でのパフォーマンステスト
```

### 4. 調査依頼のベストプラクティス

#### いつ調査を依頼すべきか

✅ **調査を依頼すべき場合**:

- 公式ドキュメントの最新情報が必要
- 技術的なベストプラクティスを確認したい
- セキュリティや互換性の確認が必要
- データスキーマや仕様の詳細が不明
- 複数の選択肢を比較したい

❌ **調査を依頼すべきでない場合**:

- 単純なシンタックスエラー（自分で解決可能）
- ドキュメントに明記されている基本的な使い方
- 既に提供されているコンテキストに含まれる情報
- 一般的な常識レベルの知識

#### 効果的な調査依頼のポイント

1. **質問は具体的に**: 曖昧な質問ではなく、具体的で答えやすい質問を
2. **コンテキストを充実させる**: 背景を説明し、なぜその調査が必要かを明確に
3. **進捗を明確に**: どこまで完了していて、何が不明かを明確に
4. **優先順位をつける**: 最も重要な質問を最初に記載
5. **次のステップを明示**: 調査後に何をするかを明確に

#### 不適切な調査依頼の例

❌ **悪い例**:

```markdown
## 調査が必要です

### 理由
よくわからない

### 調査内容
何か調べてほしい。困っています。
```

✅ **良い例**:

```markdown
## 調査が必要です

### 理由
FastAPI 0.100.0の新しいDependency Injection構文を確認する必要があります

### 調査内容
**トピック**: FastAPI 0.100.0のDependency Injection変更点

**背景**:
REST APIエンドポイントを実装中で、Dependency Injectionを使用しています。
最新版で構文が変更されたとの情報があり、正しい実装方法を確認したいです。

**質問**:
1. FastAPI 0.100.0のDependency Injectionの推奨構文は何か
2. 旧構文からの移行方法は何か
3. 非同期関数での使い方の注意点は何か

### 現在の進捗
**完了**:
- 基本的なエンドポイント構造の実装
- Pydanticモデルの定義

**次のステップ（調査後）**:
- Dependency Injectionの正しい実装
- 認証ミドルウェアの統合
```
