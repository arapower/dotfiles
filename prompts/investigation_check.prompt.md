# 調査・確認プロンプト

問題の原因究明や既存実装を理解するため、コードベース、ドキュメント、ログを体系的に調査してください。場当たり的な調査ではなく、構造化されたアプローチで効率的に情報を収集し、根本原因を特定します。バグ修正、機能追加、リファクタリング、技術負債の解消など、あらゆる開発作業の基礎となる調査を実施します。

## 使用場面

- バグの原因調査と修正
- 既存機能の仕様確認
- 新機能追加前の既存実装の理解
- パフォーマンス問題の特定
- セキュリティ脆弱性の調査
- コードレビュー前の事前確認
- レガシーコードの解析
- 技術的負債の評価

## 実行手順

### 1. 調査範囲の特定

まず、調査対象を明確に定義します：

**問題の定義**:

- 何を調査する必要があるのか（バグ、仕様、実装方法など）
- 調査の目的は何か（原因特定、仕様理解、改善提案など）
- 期待される成果物は何か（バグレポート、実装案、リファクタリング計画など）

**スコープの設定**:

- 対象となる機能やモジュールの範囲
- 関連するシステムやコンポーネント
- 調査の深さ（表層的な確認 vs 徹底的な分析）
- 時間的制約（どこまで深く調査できるか）

### 2. 関連ファイル検索

調査対象に関連するファイルを効率的に特定します：

**キーワード検索**:

- 機能名、クラス名、関数名での検索
- エラーメッセージでの検索
- ログメッセージでの検索
- コメントやドキュメント内の説明文での検索

**構造的な探索**:

- ディレクトリ構造の理解
- 命名規則に基づくファイル特定
- モジュール依存関係の追跡
- インポート/エクスポート関係の分析

**ツールの活用**:

- `grep`/`ripgrep`での全文検索
- IDEの「定義へジャンプ」「参照の検索」機能
- Git履歴の確認（`git log`, `git blame`）
- 依存関係可視化ツール

### 3. 実装パターン確認

既存のコードがどのような設計パターンや実装方針に従っているかを理解します：

**アーキテクチャの理解**:

- レイヤー構造（プレゼンテーション層、ビジネスロジック層、データアクセス層）
- デザインパターン（Factory, Strategy, Observer など）
- フレームワークの使用方法
- データフロー（データがどのように流れるか）

**コーディング規約**:

- 命名規則
- エラーハンドリング方式
- ロギング方針
- テストの書き方

**類似機能の参照**:

- 同様の機能がどう実装されているか
- 再利用可能なコンポーネントやユーティリティ
- ベストプラクティスの適用例

### 4. エッジケース調査

通常ケースだけでなく、異常系や境界値の扱いを確認します：

**異常系のチェック**:

- エラーハンドリングの実装
- バリデーションロジック
- リトライ・フォールバック処理
- タイムアウト処理

**境界値の確認**:

- 空の入力、null、undefined
- 最大値、最小値
- 特殊文字、Unicode
- 並行処理、競合状態

**テストケースの確認**:

- 既存のユニットテスト
- 統合テスト
- E2Eテスト
- テストカバレッジ

### 5. 調査結果の整理と検証

収集した情報を整理し、仮説を検証します：

**情報の構造化**:

- 調査結果のドキュメント化
- 関連ファイルのリスト作成
- データフロー図の作成
- タイムラインの整理（いつ、何が起きたか）

**仮説の検証**:

- ログやデバッグ出力での確認
- ローカル環境での再現テスト
- コードの静的解析
- 必要に応じて追加のトレース実装

### 6. 追加調査要否判定（止め時/深掘り判断）

調査は無限にできるため、「追加調査が本当に必要か」を明示的に判定します。

**追加調査が必要（追加調査）**:

- 重要な結論が**仮定**に依存している（例: 「たぶんこの関数が呼ばれている」）
- 主張に対してログ/コード/公式仕様などの**根拠不十分**な状態
- 受入条件/再現条件が未確定で、修正の正しさを検証できない
- 影響範囲が大きいのに、参照箇所や利用箇所の探索が終わっていない

**追加調査を打ち切ってよい**:

- 根拠（参照先/実測/再現）が揃い、次のアクション（修正/提案/実装）が明確
- リスクが低く、実装→テストで短いフィードバックループが回せる

**判定メモ（最小フォーマット）**:

```markdown
- 結論: {現時点の結論}
- 根拠: {ファイル/ログ/コマンド結果}
- 仮定: {未検証の前提があれば}
- 追加調査: {必要/不要}（理由）
```

## 期待される成果

- **正確な現状把握**: システムの現在の実装と動作の完全な理解
- **根本原因の特定**: 表面的な症状ではなく、真の原因を発見
- **効率的な作業計画**: 調査結果に基づく適切な修正・改善計画
- **リスクの事前把握**: 変更による影響範囲の特定
- **知識の蓄積**: チーム全体で共有できる知見の獲得

## 注意事項

- **仮説思考**: 闇雲に調査せず、仮説を立てて検証するアプローチを取る
- **調査の記録**: 何を調べて何が分かったか、必ず記録に残す
- **時間管理**: 深く調査しすぎて時間を浪費しないよう注意
- **視野の広さ**: 一つの箇所だけでなく、システム全体への影響を考慮
- **バージョン管理**: 調査対象のコードのバージョンを明確にする
- **再現性**: 問題を再現可能な状態にすることが最優先
- **チームへの共有**: 調査結果は適切にチームに共有する
