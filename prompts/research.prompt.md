# 調査プロンプト（統合版）

技術的な問題解決や意思決定に必要な情報を、Web検索、リポジトリ内検索、公式ドキュメントなど複数の情報源から効率的に収集し、その信頼性を検証し、統合して活用可能な知識にしてください。単なる検索ではなく、情報の品質評価、複数ソースの照合、実践的な検証を通じて、確実な技術的裏付けを提供します。新しい技術の採用、バグの原因究明、最適な実装方法の選択など、あらゆる技術的判断の基盤となる調査を実施します。

## 使用場面

- 技術選定時のライブラリやフレームワークの調査
- バグの原因究明とトラブルシューティング
- APIの使用方法やパラメータの確認
- セキュリティベストプラクティスの調査
- パフォーマンス最適化の方法論
- 既存実装の理解（コードベース内検索）
- 新しい技術トレンドのキャッチアップ
- エラーメッセージの解決方法
- アーキテクチャパターンの調査
- 互換性や依存関係の確認

## 実行手順

### 1. 調査目的の明確化

効率的な調査のため、何を知りたいのかを明確にします：

**調査目的の定義**:

```markdown
✅ 明確な調査目的の例:

**悪い例:**
「Reactについて調べる」
→ 範囲が広すぎて、何を調べるべきか不明確

**良い例:**
「React 18の新機能『Concurrent Rendering』の
実装方法と既存コードへの影響を調査する」
→ 具体的で、調査のゴールが明確
```

**5W1Hで整理**:

- **What（何を）**: どの技術・機能について調べるのか
- **Why（なぜ）**: なぜ調査が必要なのか（背景・目的）
- **Where（どこで）**: どこに情報があるか（情報源の見当）
- **When（いつ）**: いつの情報が必要か（最新版？特定バージョン？）
- **Who（誰が）**: 誰が使うのか（開発者向け？ユーザー向け？）
- **How（どのように）**: どう活用するのか（実装？評価？）

**調査の種類を特定**:

```
1. **概要調査**: 技術の全体像を把握
   例: 「GraphQLとRESTの違い」

2. **深掘り調査**: 特定の機能や実装方法を詳細に
   例: 「Apollo ClientのキャッシュAPIの使用方法」

3. **問題解決調査**: エラーやバグの原因と解決策
   例: 「TypeScript error TS2345の解決方法」

4. **比較検討調査**: 複数の選択肢を評価
   例: 「Prisma vs TypeORMの比較」

5. **最新動向調査**: 技術トレンドやアップデート情報
   例: 「Next.js 14の新機能」
```

**調査スコープの設定**:

```markdown
調査範囲を明確にする:
- 必須情報: 最低限必要な情報
- 優先情報: できれば知りたい情報
- 参考情報: 時間があれば調べる情報

調査の深さを決める:
- サーベイレベル: 概要だけ把握
- 実装レベル: 実際にコードが書けるレベル
- エキスパートレベル: 内部実装まで理解
```

### 2. 情報源の選定

調査目的に応じて、適切な情報源を選択します：

**情報源の分類と優先順位**:

**1. 公式ドキュメント（最優先）**:

```
信頼性: ★★★★★
利点: 
- 最も正確で信頼できる
- バージョン情報が明確
- 公式のベストプラクティス

対象:
- 公式ドキュメントサイト
- GitHub公式リポジトリのREADME/Wiki
- APIリファレンス
- Migration Guide

例:
- https://react.dev/
- https://docs.python.org/
- https://www.typescriptlang.org/docs/
```

**2. 技術ブログ・記事（信頼できるソース）**:

```
信頼性: ★★★★☆
利点:
- 実践的なユースケース
- トラブルシューティング事例
- 複数の視点

対象:
- 公式ブログ（Vercel Blog、Google Developers）
- 有名エンジニアのブログ
- Medium、Zenn、Qiita（高評価記事）
- Dev.to

注意点:
- 公開日を確認（古い情報の可能性）
- 著者の信頼性を評価
```

**3. コミュニティ・Q&A（問題解決）**:

```
信頼性: ★★★☆☆
利点:
- 実際の問題と解決策
- コミュニティの知見
- エッジケースの情報

対象:
- Stack Overflow
- GitHub Issues / Discussions
- Reddit (r/programming, r/javascript など)
- Discord / Slack コミュニティ

注意点:
- 複数の回答を比較
- 投票数や採用マークを参考に
- 古い情報でないか確認
```

**4. リポジトリ内検索（既存実装）**:

```
信頼性: ★★★★☆（自社コード）
利点:
- 実際に動作しているコード
- プロジェクト固有の実装パターン
- チームの慣習を把握

対象:
- 既存の類似実装
- ユーティリティ関数
- テストコード
- コード内コメント

ツール:
- VS Codeのファイル検索
- grep / ripgrep
- GitHub Code Search
```

**5. ソースコード（深掘り）**:

```
信頼性: ★★★★★（ただし読解力が必要）
利点:
- 最も正確な情報
- ドキュメントにない動作を確認
- バグの原因究明

対象:
- GitHub上のライブラリソース
- node_modules内のコード
- TypeScript型定義ファイル

注意点:
- 時間がかかる
- 高度な読解力が必要
```

**情報源選定のフローチャート**:

```
調査目的を決める
  ↓
公式ドキュメントを確認
  ↓
  ├─ 情報が十分 → 終了
  ├─ 情報が不足 → 技術記事を探す
  ├─ エラー解決 → Stack Overflow / GitHub Issues
  ├─ 既存実装   → リポジトリ内検索
  └─ 深い理解   → ソースコード読解
```

### 分野別ツールセット（選び方）

調査は「何を調べるか」によって最適なツールが変わります。まずドメインとリスクで絞り込み、次に再現/検証の速さで選びます。

**Security（脆弱性/設定不備）**:

- 依存関係の脆弱性: OSV / npm audit / pip-audit（プロジェクトに応じて）
- 静的解析: semgrep 等（採用済みなら）
- コンテナ/ IaC: trivy 等（採用済みなら）

**Infra / Terraform（IaC）**:

- `terraform fmt` / `terraform validate` / `terraform plan`
- `tflint` / `terragrunt`（利用している場合）
- 変更影響の確認: module 呼び出し元/vars の探索（grep/VS Code検索）

**Python**:

- `pytest`（再現/回帰）
- `ruff` / `flake8` / `mypy`（導入済みのものを優先）
- 依存: `pip`/`pip-tools`（運用方針に従う）

**Node / TypeScript**:

- `npm test` / `npm run lint` / `eslint` / `tsc`（導入済みのものを優先）
- lockfile（package-lock.json 等）と CI 設定の整合確認

**DB（SQL/スキーマ/性能）**:

- スキーマ: migration / DDL の差分確認
- 性能: `EXPLAIN` / `EXPLAIN ANALYZE`（可能な環境で）
- データ整合: 制約/インデックス/トランザクション境界の確認

**選択の目安**:

- まず「最短で根拠が取れる」ツール（既存テスト/ログ/grep）→ 次に重い調査（静的解析/深掘り）
- 低リスク: 速い検証を優先 / 高リスク: 根拠の多重化（複数ソース照合）を優先

### 3. 検索と収集

効率的な検索テクニックで必要な情報を収集します：

**Web検索のテクニック**:

**基本的な検索クエリ**:

```
# 基本パターン
「[技術名] [機能] [バージョン]」
例: "React 18 useTransition example"

# エラー解決
「[エラーメッセージ] [技術名]」
例: "TypeError: Cannot read property 'map' of undefined React"

# 比較検討
「[技術A] vs [技術B] [比較軸]」
例: "Prisma vs TypeORM performance 2024"

# ベストプラクティス
「[技術名] best practices [年]」
例: "Next.js best practices 2024"
```

**Google検索の高度な演算子**:

```
# サイト指定
site:github.com React hooks
site:stackoverflow.com TypeScript generic

# 完全一致
"exact phrase here"

# 除外
React -class components

# ファイルタイプ
filetype:pdf React architecture

# 期間指定（Googleの検索ツール）
「ツール」→「期間指定」→「1年以内」
```

**GitHub検索のテクニック**:

```
# リポジトリ内検索
repo:facebook/react useEffect

# 特定の言語
language:typescript authentication

# スター数でフィルタ
stars:>1000 REST API client

# トピック検索
topic:machine-learning topic:python

# Issueやプルリクエスト
is:issue label:bug state:open

# コード検索の例
path:src/ extension:ts useAuth
```

**リポジトリ内検索（VS Code）**:

```bash
# 全文検索
Ctrl+Shift+F (Windows/Linux)
Cmd+Shift+F (Mac)

# 正規表現検索
function\s+\w+Auth\w*

# ファイル名検索
Ctrl+P (Windows/Linux)
Cmd+P (Mac)
**/*auth*.ts

# Grepコマンド
# 関数定義を検索
grep -r "function.*Auth" src/

# インポート文を検索
grep -r "import.*useState" src/

# ファイルタイプを指定
grep -r --include="*.ts" "interface User" src/
```

**Stack Overflow検索のコツ**:

```
# タグを組み合わせ
[typescript] [generics] type inference

# エラーメッセージで検索
"Cannot find module" typescript paths

# スコアでソート
検索結果ページで「Votes」でソート

# 採用済み回答を優先
検索結果の緑のチェックマークを確認
```

**収集する情報のチェックリスト**:

```markdown
□ 基本情報
  □ 技術の概要・目的
  □ 主な機能
  □ 使用方法（基本的な例）

□ 実装情報
  □ インストール方法
  □ 設定方法
  □ APIリファレンス
  □ コード例

□ 制約・注意事項
  □ ブラウザ/環境の互換性
  □ バージョン要件
  □ 既知の問題
  □ パフォーマンス特性

□ 関連情報
  □ 公式ドキュメントのリンク
  □ 参考記事・チュートリアル
  □ 関連ライブラリ
  □ 代替技術
```

### 4. 信頼性の検証

収集した情報の正確性と信頼性を評価します：

**情報の信頼性チェックリスト**:

**1. ソースの評価**:

```
✅ 信頼できるソース:
- 公式ドキュメント
- 著名な技術者・企業のブログ
- 高評価の技術記事
- Stack Overflowの高投票回答
- GitHub公式リポジトリ

⚠️ 注意が必要なソース:
- 個人ブログ（著者不明）
- 低評価の記事
- 古い情報（3年以上前）
- 一次情報がない引用のみの記事
```

**2. 鮮度の確認**:

```
チェックポイント:
□ 公開日・更新日を確認
□ 対象のバージョンを確認
□ 現在も有効な情報か確認

例:
❌ "React 16でのベストプラクティス（2019年）"
   → React 18では通用しない可能性

✅ "React 18での新しいアプローチ（2024年）"
   → 最新情報
```

**3. 複数ソースの照合**:

```
手順:
1. 最低3つの独立したソースを確認
2. 共通する内容を抽出
3. 矛盾する情報を特定
4. 公式ソースで最終確認

例:
情報源A: 「Xを使うべき」
情報源B: 「Xを使うべき」
情報源C: 「Yの方が良い」
公式ドキュメント: 「Xを推奨」
→ Xが正解の可能性が高い
```

**4. 実践的な検証**:

```
可能であれば実際に試す:

□ サンプルコードを実行
□ 提案された解決策をテスト
□ パフォーマンスを計測
□ エッジケースを確認

例:
# 実際に試してみる
npm install library-name
# サンプルコードを実行
# 動作を確認
# ベンチマーク測定
```

**5. コミュニティの反応を確認**:

```
GitHub:
□ スター数・フォーク数
□ Issue数と対応状況
□ 最終更新日
□ コントリビューター数
□ メンテナンス状況

npm / PyPI:
□ 週間ダウンロード数
□ 依存パッケージ数
□ 脆弱性情報

例:
✅ 良い指標:
- 10k+ stars
- 週次でアップデート
- Issueへの迅速な対応
- 100k+ weekly downloads

⚠️ 注意の指標:
- 長期間更新なし
- 大量の未解決Issue
- セキュリティ脆弱性
- 低いダウンロード数
```

**信頼性スコアリング例**:

```
評価項目（各10点満点）:

1. ソースの権威性
   公式: 10点、著名ブログ: 7点、不明: 3点

2. 情報の鮮度
   1年以内: 10点、1-3年: 7点、3年以上: 3点

3. 複数ソースでの一致
   3つ以上一致: 10点、2つ一致: 7点、1つのみ: 3点

4. 実践的検証
   検証済み: 10点、部分検証: 7点、未検証: 3点

5. コミュニティ評価
   高評価: 10点、中評価: 7点、低評価: 3点

合計40点以上: 信頼できる
合計25-39点: 追加検証が必要
合計24点以下: 他の情報源を探す
```

## ベストプラクティス

### 調査の効率化

```
1. まず公式ドキュメントを確認
2. 複数の情報源を並行して調査
3. 古い情報を避ける（日付確認）
4. コミュニティの評価を参考に
5. 可能なら実際に試す
```

### 情報の記録

```
- 調査結果を文書化
- 参考URLを保存
- コード例を保存
- 日付とバージョンを記録
- チームで共有
```

### 継続的な学習

```
- 定期的に最新情報をチェック
- RSS/ニュースレターを購読
- コミュニティに参加
- アップデート情報を追跡
```

## アンチパターン

### 1. 情報源を確認しない

```
❌ 避けるべき:
検索結果の最初の記事だけを鵜呑み

✅ 推奨:
複数の信頼できるソースを確認し、照合する
```

### 2. 古い情報を使う

```
❌ 避けるべき:
2020年のReact記事を2024年に参考にする

✅ 推奨:
情報の日付を確認し、最新の情報を優先する
```

### 3. 実践的な検証をしない

```
❌ 避けるべき:
理論だけ調べて実際に試さない

✅ 推奨:
サンプルコードを実行し、動作を確認する
```

### 4. 調査結果を記録しない

```
❌ 避けるべき:
頭の中だけで調査結果を保持

✅ 推奨:
ドキュメント化し、チームで共有できるようにする
```
