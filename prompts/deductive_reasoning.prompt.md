# 演繹的推論プロンプト

一般的な原則や前提から、論理的な規則を適用して具体的な結論を必然的に導き出してください。前提が真であれば結論も必ず真となる推論方法を用いて、テストケースの網羅的な導出、型安全性の保証、潜在的な脆弱性の発見を行います。

## 実行手順

### 1. 前提（一般原則）の特定

推論の出発点となる前提や原則を明確に特定します：

**ドメインルールの抽出**:

- ビジネスルールや業務ルール（「注文は必ず顧客に紐づく」）
- システム制約（「同時接続数は1000まで」）
- セキュリティポリシー（「すべてのAPIエンドポイントは認証が必要」）
- データ整合性制約（「外部キーは必ず存在する親レコードを参照する」）

**技術的な前提**:

- 型システムのルール（「NullPointerExceptionは null に対するメソッド呼び出しで発生」）
- プログラミング言語の仕様（「Pythonの辞書は3.7以降挿入順を保持」）
- フレームワークの制約（「Reactのhooksはトップレベルでのみ呼び出せる」）
- プロトコルの仕様（「HTTPSは暗号化された通信を保証」）

**論理的公理**:

- 数学的な法則（「A かつ B ならば A」）
- 集合論の基本法則
- 論理演算のルール（ド・モルガンの法則など）
- 推移律、対称律などの性質

**明示的な仕様**:

- 関数のプリコンディション（事前条件）
- ポストコンディション（事後条件）
- クラス不変条件（class invariant）
- インターフェース契約

### 2. 論理規則の適用

確立された論理規則を用いて推論を進めます：

**基本的な推論規則**:

- モダス・ポネンス: 「AならばB」かつ「A」ならば「B」
- モダス・トレンス: 「AならばB」かつ「¬B」ならば「¬A」
- 三段論法: 「AならばB」かつ「BならばC」ならば「AならばC」
- 選言三段論法: 「AまたはB」かつ「¬A」ならば「B」

**型システムの推論**:

```
前提: すべての関数は型シグネチャを持つ
前提: f: (int) -> string という型シグネチャ
前提: x は int 型
結論: f(x) は string 型を返す
```

**制約伝播**:

```
前提: x > 10
前提: y = x + 5
結論: y > 15
```

**セキュリティ推論の例**:

```
前提: すべてのAPIエンドポイントは認証が必要
前提: /api/users はAPIエンドポイントである
結論: /api/users は認証が必要である
```

### 3. 結論の導出

論理的な手順を追って、必然的な結論を導きます：

**段階的な推論**:

- 各ステップで一つの論理規則のみを適用
- 中間結論を明示的に記述
- 推論の連鎖を追跡可能にする
- 飛躍のない論理展開

**テストケース導出の例**:

```
前提1: ユーザー登録には、メールアドレスとパスワードが必須
前提2: メールアドレスは形式が正しくなければならない
前提3: パスワードは8文字以上でなければならない

結論1: メールアドレスが空の場合、登録は失敗する
結論2: メールアドレスの形式が不正な場合、登録は失敗する
結論3: パスワードが7文字以下の場合、登録は失敗する
結論4: パスワードが空の場合、登録は失敗する
結論5: すべての条件を満たす場合のみ、登録は成功する
```

**エッジケース特定の例**:

```
前提: 配列のインデックスは0からlength-1まで
前提: この関数は arr[i+1] にアクセスする
前提: i は 0 から length-1 の範囲でループする

結論: i = length-1 のとき、arr[length] にアクセスする
結論: これは配列の範囲外アクセスである（off-by-one error）
```

**セキュリティ脆弱性の推論**:

```
前提: ユーザー入力はSQLクエリに直接埋め込まれている
前提: SQLインジェクションは、特殊文字でクエリ構造を変更できる
前提: 入力のサニタイゼーションが行われていない

結論: このコードはSQLインジェクションの脆弱性を持つ
結論: 攻撃者は任意のSQLクエリを実行できる可能性がある
```

### 4. 妥当性検証

導出した結論の論理的な妥当性を検証します：

**推論の正当性チェック**:

- 各ステップの論理規則は正しく適用されているか
- 前提から結論への推論に飛躍はないか
- 暗黙の前提が紛れ込んでいないか
- 循環論法になっていないか

**前提の確認**:

- すべての前提は本当に真か？
- 仕様書や実装で確認できるか
- 古い情報や誤った理解に基づいていないか
- 例外や条件が存在しないか

**反例の不在確認**:

- 前提が真だが結論が偽となるケースは存在するか？
- もし存在すれば、推論に誤りがある
- 実装やテストで反例を探す

**形式的検証**:

- 可能であれば、ツールで検証（型チェッカー、静的解析）
- 単体テストで結論を確認
- プロパティベーステストで網羅的に検証
- モデル検査ツールで状態空間を探索

## 期待される成果

### 論理的に必然な結論

- 前提が正しければ確実に正しい結論
- 見落としのない網羅的な分析
- 予測可能で再現性のある推論
- 第三者が検証可能な論理展開

### 確実な推論による品質向上

- バグの事前発見と予防
- テストケースの網羅性向上
- セキュリティホールの体系的な発見
- 仕様の曖昧さや矛盾の検出
- リファクタリングの安全性保証

### 具体的な成果物

- 仕様ベースの完全なテストスイート
- 型安全性が保証されたコード
- セキュリティチェックリスト
- 形式検証済みの重要ロジック
- エッジケースの完全なカタログ

## 注意事項

### 前提の妥当性が重要

- 演繹的推論は前提が真であることが絶対条件
- 前提が誤っていれば、論理的に正しくても結論は誤り
- 「Garbage In, Garbage Out」の原則
- 仕様書や実装を常に確認する

### 適用範囲の限界

- 演繹的推論は、前提に含まれる情報以上のことは導けない
- 新しい知見や創造的な解決策は得られない
- 既知のルールから導けることのみ
- 未知の問題には帰納的推論や類推思考が必要

### 形式と実践のギャップ

- 理論的には正しくても、実装にバグがある可能性
- コンパイラやツールにもバグは存在する
- 最終的には実際のテストで確認が必要
- 形式検証と動的テストの両方が重要

### 複雑さの管理

- 推論が長くなると追跡が困難
- 中間結論を明示的に記述
- ツールやフレームワークの活用
- 自動化できる部分は自動化（型チェッカーなど）
