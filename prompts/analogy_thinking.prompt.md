# 類推思考プロンプト

過去の経験や既知のパターンから、現在直面している問題との類似性を見出し、その知見を応用してください。完全に新しい解決策を編み出すのではなく、既に実績のある手法やパターンを適切に転用することで、効率的かつ信頼性の高い実装を実現します。デザインパターンの選定、アーキテクチャ設計、問題解決など、あらゆる開発活動の基礎となる思考法です。

## 使用場面

- デザインパターンの選定と適用
- 設計上の問題に対する既知の解決策の適用
- 新しい技術や概念の理解（既知のものとの比較）
- コードレビュー時の改善提案
- バグの原因推定（類似の過去事例から）
- アーキテクチャ設計の決定
- ベストプラクティスの適用
- 技術選定時の評価

## 実行手順

### 1. 問題の構造分析

まず、現在の問題を構造化して理解します：

**問題の抽象化**:

- 具体的な実装の詳細を一旦脇に置く
- 問題の本質的な要素を抽出する
- 主要な制約条件を特定する
- 解決すべき核心的な課題は何か？

**問題のカテゴリ化**:

- この問題はどのカテゴリに属するか？
  - データ構造の選択
  - 並行処理の制御
  - エラーハンドリング
  - パフォーマンス最適化
  - セキュリティ対策
  - ユーザビリティ改善
- 既知の問題分類に当てはまるか？

**要素の分解**:

- 問題を構成する要素を列挙
- 各要素間の関係性を明確化
- 入力と出力、前提条件と制約
- 副作用や影響範囲

### 2. 類似ケースの探索

過去の経験や既知の事例から、類似のケースを探します：

**自身の経験からの探索**:

- 過去に解決した類似の問題はないか？
- 以前のプロジェクトで似た実装をしなかったか？
- 同じようなエラーや問題に遭遇したことは？
- 成功した実装パターンは何だったか？

**チームの知見の活用**:

- チームメンバーが同様の問題を解決した経験は？
- 社内のドキュメントやナレッジベースに事例は？
- コードレビューで見た類似の実装は？
- チャットやSlackの過去ログに関連する議論は？

**外部リソースの調査**:

- Stack Overflowでの類似の質問
- GitHubでのオープンソース実装
- 技術ブログや記事での解説
- 書籍やドキュメントでのパターン
- 学術論文での研究成果

**デザインパターンとの照合**:

- GoFパターン（23のデザインパターン）
- エンタープライズアプリケーションアーキテクチャパターン
- ドメイン駆動設計のパターン
- マイクロサービスパターン
- クラウドデザインパターン

### 3. 共通パターンの抽出

類似ケースから共通する要素やパターンを抽出します：

**構造的な類似性**:

- 同じような構造やアーキテクチャが使われているか？
- データの流れ方は似ているか？
- コンポーネント間の関係性は？
- レイヤー構造や責任の分離方法は？

**問題解決のアプローチ**:

- どのような手順で問題を解決しているか？
- キーとなる技術やアルゴリズムは何か？
- トレードオフの考え方は？
- 例外ケースへの対処方法は？

**成功要因と失敗要因**:

- なぜその解決策が有効だったのか？
- どのような条件下でうまく機能したか？
- 失敗した事例では何が問題だったか？
- どのような落とし穴があったか？

### 4. 適用と調整

抽出したパターンを現在の問題に適用し、必要に応じて調整します：

**直接適用の可能性評価**:

- パターンをそのまま適用できるか？
- 技術スタックは適合しているか？
- チームのスキルセットで実装可能か？
- プロジェクトの制約に合致しているか？

**カスタマイズと調整**:

- 現在の文脈に合わせた調整が必要な部分は？
- スケールの違いによる修正点は？
- 追加で考慮すべき制約は？
- 既存コードベースとの整合性は？

**段階的な適用**:

- まず小規模で試してみる
- プロトタイプやスパイクで検証
- フィードバックを得て調整
- 本番適用前のレビューとテスト

**ドキュメント化**:

- どのパターンを参考にしたか
- なぜそのパターンを選んだか
- どのように調整したか
- 将来の参考のために記録

### 5. 検証と学習

適用した結果を検証し、学びを蓄積します：

**結果の評価**:

- 期待通りに機能したか？
- パフォーマンスは満足できるか？
- 保守性は向上したか？
- チームは理解しやすいか？

**類推の妥当性の検証**:

- 類似性の認識は正しかったか？
- 見落としていた相違点はなかったか？
- 適用する際の調整は適切だったか？
- より良い類推があったか？

**ナレッジの蓄積**:

- 今回の経験を記録する
- 次回の類推のための参考資料
- チームでの共有とレビュー
- ベストプラクティスの更新

## 期待される成果

- **実績のある手法の活用**: 既に成功が証明された方法を使用することで、リスクを低減
- **開発効率の向上**: ゼロから考えるのではなく、既存の知見を活用して迅速に実装
- **品質の保証**: ベストプラクティスに基づいた実装により、バグや問題を削減
- **学習の加速**: パターンを理解することで、より深い技術理解が得られる
- **車輪の再発明の回避**: 既存の優れた解決策を活用し、無駄な労力を削減
- **コミュニケーションの効率化**: パターン名で会話できることで、チーム内の意思疎通が円滑に

## 注意事項

- **表面的な類似に騙されない**: 見た目は似ていても、本質的に異なる問題の可能性
- **文脈の違いを考慮**: 同じパターンでも、異なる文脈では異なる結果をもたらす
- **過度な一般化を避ける**: すべての状況に当てはまるわけではない
- **盲目的な適用を避ける**: パターンを理解せずに機械的に適用しない
- **新しいアプローチの可能性**: 既存のパターンにとらわれすぎて、より良い方法を見逃さない
- **過剰な抽象化**: 将来の拡張を見越しすぎて、現在の問題を複雑にしない
- **チームの理解**: 選んだパターンをチーム全体が理解できるか確認
