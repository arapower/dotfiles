# 詳細への感度プロンプト

コードやシステムの動作における微細な違い、異常、不整合を敏感に検出してください。off-by-oneエラー、メモリリーク、わずかな性能劣化、境界値での異常動作など、見落とされがちだが重大な影響を持つ問題を発見します。

## 実行手順

### 1. 期待値の明確化

何が「正常」で何が「異常」かを判断するため、期待される状態を明確にします：

**仕様の理解**:

- 正式な仕様書や要件定義
- 設計ドキュメントやAPI仕様
- 既存の実装の振る舞い（リグレッション検出時）
- 業界標準やベストプラクティス

**暗黙的な期待**:

- 「クラッシュしない」「データが壊れない」などの基本的な品質
- パフォーマンス特性（応答時間、スループット）
- リソース使用量の妥当な範囲
- ユーザーエクスペリエンスの一貫性

**境界条件の特定**:

- 最小値と最大値
- 空のケース（空配列、空文字列、null）
- エッジケース（配列の最初と最後、型の境界値）
- 特殊な入力（負の数、巨大な値、特殊文字）

**不変条件の確認**:

- システムが常に満たすべき性質
- データ構造の整合性制約
- ビジネスロジックの制約
- 型安全性の保証

### 2. 実際の観察

システムやコードの実際の動作を注意深く観察します：

**コードレビュー時の観察ポイント**:

```python
# ループの境界チェック
for i in range(len(arr)):
    if arr[i] == target:
        next_value = arr[i+1]  # ⚠️ i = len(arr)-1 の時、範囲外アクセス

# リソースのクリーンアップ
file = open('data.txt')
data = file.read()
# ⚠️ close() が呼ばれていない（例外時にリークする可能性）

# 型の暗黙的変換
result = user_input / 10  # ⚠️ user_input が文字列の場合、エラーまたは予期しない動作

# nullチェック
user = getUser(id)
print(user.name)  # ⚠️ user が null の可能性を考慮していない
```

**動的な動作の観察**:

- ログ出力の内容と頻度
- メモリ使用量の推移（緩やかな上昇 = リーク？）
- CPU使用率の変動
- レスポンスタイムの分布（外れ値の存在）
- エラー率の変化
- データベースクエリの実行回数（N+1問題？）

**ツールを使った観察**:

- デバッガでのステップ実行
- プロファイラでのホットスポット分析
- メモリプロファイラでのアロケーション追跡
- 静的解析ツールの警告
- Lintツールの指摘
- カバレッジレポートの未テスト箇所

**UIの観察**:

- ピクセル単位での配置ずれ
- 一瞬のちらつきや再描画
- アニメーションのカクつき
- ローディング状態の表示タイミング
- フォーカスの移動順序
- キーボード操作での挙動

### 3. 差異の検出

期待値と実際の観察結果を比較し、違いを検出します：

**数値的な差異**:

```
期待: レスポンスタイム < 100ms
実測: 平均 95ms、最大 250ms
→ ⚠️ 最大値が期待を大きく超えている

期待: メモリ使用量は一定
実測: 1時間で 100MB → 150MB へ増加
→ ⚠️ メモリリークの可能性

期待: エラー率 < 0.1%
実測: 通常 0.05%、特定時間帯 0.5%
→ ⚠️ 時間帯依存の問題の可能性
```

**構造的な差異**:

```typescript
// パターンの不一致
class UserService {
  async getUser() { /* ... */ }
  async updateUser() { /* ... */ }
  deleteUser() { /* ... */ }  // ⚠️ 他と異なり async でない
}

// 命名の不一致
const userId = getUserId();
const user_name = getUserName();  // ⚠️ camelCase と snake_case の混在
const UserEmail = getUserEmail(); // ⚠️ 大文字で始まる変数名
```

**動作の不一致**:

```javascript
// 期待: すべてのケースでバリデーション実施
function processData(data) {
  if (data.type === 'A') {
    validate(data);
    return handleTypeA(data);
  } else if (data.type === 'B') {
    return handleTypeB(data);  // ⚠️ バリデーションがない
  }
}
```

**境界での異常**:

```python
# 境界値テスト
def get_grade(score):
    if score >= 90: return 'A'
    elif score >= 80: return 'B'
    elif score >= 70: return 'C'
    elif score >= 60: return 'D'
    else: return 'F'

# テスト
assert get_grade(90) == 'A'  # ✓
assert get_grade(89) == 'B'  # ✓
assert get_grade(89.9) == 'B'  # ⚠️ もし score が int のみを想定なら、これは想定外
assert get_grade(-10) == 'F'  # ⚠️ 負の点数は想定されているか？
```

### 4. 影響の評価

検出した差異が実際にどの程度の問題かを評価します：

**重大度の判定**:

- **Critical**: データ損失、セキュリティ侵害、システムクラッシュ
- **High**: 主要機能の不具合、パフォーマンスの大幅な劣化
- **Medium**: 一部機能の不具合、軽微なパフォーマンス問題
- **Low**: UI の小さなずれ、非本質的な問題
- **Info**: 改善の余地、ベストプラクティスからの逸脱

**影響範囲の確認**:

- どのユーザーが影響を受けるか（全体、一部、特定条件下）
- どのような条件で発生するか（頻度、再現性）
- 他の機能への波及効果はあるか
- データの整合性に影響するか
- セキュリティへの影響はあるか

**緊急性の判定**:

- すぐに修正が必要か
- リリースをブロックすべきか
- 回避策は存在するか
- 既存ユーザーへの影響は大きいか

**トレードオフの考慮**:

- 修正のコストと影響のバランス
- リスクと利益の評価
- 完璧を求めすぎていないか
- 本質的な問題か、スタイルの問題か

## 期待される成果

### 微細なバグの発見

- off-by-oneエラーの検出
- 境界値での異常動作の発見
- メモリリークやリソースリークの特定
- 競合状態（race condition）の検出
- null参照や未定義値の問題
- 型の暗黙的変換による問題
- エッジケースでのクラッシュ

### 品質向上

- バグの早期発見によるコスト削減
- ユーザー体験の一貫性向上
- パフォーマンスの最適化
- セキュリティの強化
- コードの可読性と保守性の向上
- テストカバレッジの向上

### 予防的な改善

- 潜在的な問題の事前発見
- 技術的負債の早期対処
- リファクタリング機会の特定
- アーキテクチャ上の問題の検出

## 注意事項

### 完璧主義のバランス

- すべての微細な問題を修正する必要はない
- 影響度と修正コストのバランス
- 「完璧」を追求しすぎて進捗が止まらないように
- 本質的な問題に集中する

### コンテキストの理解

- なぜそのコードが書かれたのか
- 意図的な設計判断の可能性
- レガシーコードの歴史的経緯
- 修正による影響範囲

### 過剰な検出の回避

- false positive（誤検出）に注意
- ツールの警告をすべて鵜呑みにしない
- 実際の問題かどうかの検証
- チーム内での合意形成

### 継続的な学習

- 新しいバグパターンの学習
- ツールの使い方の習熟
- ベストプラクティスのアップデート
- 他者のレビューから学ぶ
